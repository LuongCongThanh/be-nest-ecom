① Dependency Injection — Tại sao NestJS không cần new?

DI là thứ khiến nhiều frontend dev bối rối nhất khi học NestJS. Hãy hiểu nó từ vấn đề mà nó giải quyết.

Thế giới không có DI — bạn tự quản lý mọi thứ

// ❌ Cách làm KHÔNG dùng DI
class AuthController {
  private authService: AuthService;

  constructor() {
    // Bạn phải tự new() mọi dependency
    const prismaService = new PrismaService();
    const tokenService  = new TokenService(jwtSecret);
    const userRepo      = new UserRepository(prismaService);
    this.authService    = new AuthService(tokenService, userRepo);
  }
}

Vấn đề: nếu AuthService cần thêm dependency, bạn phải sửa mọi nơi đang new AuthService(). Với 10 class dùng AuthService — sửa 10 chỗ.

Thế giới có DI — NestJS lo hết

// ✅ Cách NestJS làm — code thật từ be-nest-ecom
@Injectable()
export class AuthController {
  constructor(private readonly authService: AuthService) {}
  // NestJS đọc TypeScript type → tự tìm AuthService → tự new() và truyền vào
}

@Injectable()
export class AuthService {
  constructor(
    private readonly tokenService: TokenService,
    private readonly prisma: PrismaService,
    private readonly userRepository: UserRepository,
  ) {}
}
🧩 Analogy — so sánh với React

Trong React bạn dùng Context: useContext(AuthContext) — component không cần biết AuthContext được tạo ra ở đâu, chỉ cần "khai báo nhu cầu" và React cung cấp.

DI trong NestJS y hệt vậy: class khai báo cần gì trong constructor, NestJS Container (= React Context Provider) tự cung cấp instance phù hợp. Bạn không cần new, không cần truyền qua nhiều lớp.

NestJS Container hoạt động như thế nào?

Khi app boot, NestJS xây một "container" — bản đồ biết class nào → instance nào:

// NestJS Container (đơn giản hóa)
{
  PrismaService    → instance#1 (singleton)
  TokenService     → instance#2
  UserRepository   → instance#3
  AuthService      → instance#4 (nhận #2, #1, #3)
  AuthController   → instance#5 (nhận #4)
}

Mỗi Provider là singleton mặc định — chỉ tạo 1 lần, dùng lại mãi:

// AuthController và JwtStrategy
// CÙng dùng 1 instance TokenService
// Không tạo 2 object riêng biệt

// Lợi ích: connection pool (Prisma)
// được share, không bị duplicate
💡
Singleton = mọi nơi inject PrismaService đều nhận cùng 1 object. Database connection pool không bị tạo lại nhiều lần.

Điều kiện để DI hoạt động

Điều kiệnCách làmNếu thiếu

② Guard Pipeline — Request bị chặn ở đâu và khi nào?

Guard là lớp quyết định: request này có được phép tiếp tục không? Nó chạy sau middleware nhưng trước handler.

Toàn bộ request pipeline — thứ tự chính xác

1

Middleware (nếu có)

Chạy trước mọi thứ. Không biết route là gì. Dùng cho: CORS headers, request logging, rate limiting toàn cục. Trong project: CORS được setup ở main.ts.

2

Guard — JwtAuthGuard của bạn

Đây là nơi auth xảy ra. Guard đọc request.headers.authorization, verify JWT. Nếu route có @Public() → bỏ qua. Nếu token invalid → throw UnauthorizedException → response 401, handler không bao giờ chạy.

// JwtAuthGuard kiểm tra decorator @Public()
const isPublic = this.reflector.getAllAndOverride(IS_PUBLIC_KEY, [
  context.getHandler(),  ← đọc metadata từ method
  context.getClass(),    ← đọc metadata từ class
]);
if (isPublic) return true; ← cho qua ngay
3

Interceptor (nếu có)

Bọc xung quanh handler — có thể chạy code trước VÀ sau handler. Dùng cho: logging execution time, transform response shape, cache. Trong project hiện tại chưa dùng nhiều.

4

Pipe — ValidationPipe

Validate và transform input. ValidationPipe được đăng ký global ở main.ts với whitelist: true — tự động loại bỏ field lạ không có trong DTO. Dữ liệu sai → 400 Bad Request với chi tiết lỗi.

// main.ts — global cho toàn app
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,     ← xóa field không có trong DTO
  forbidNonWhitelisted: true, ← throw 400 nếu có field lạ
  transform: true,     ← tự convert "3" thành số 3
}));
5

Handler — method trong Controller ✅

Request đến đây rồi thì đã: ✓ Authenticated (hoặc Public) ✓ Input validated. Bạn chỉ cần xử lý business logic.

⚠️
Tại sao default-deny quan trọng hơn default-allow? Nếu mặc định là allow (phải thêm @UseGuards() vào từng route), developer quên một route → lỗ hổng bảo mật production. Nếu mặc định là deny (phải thêm @Public() để mở), quên thêm = route bị block → lỗi này lộ ngay khi test, không lên production.

So sánh: Guard vs Middleware — khi nào dùng cái nào?

MiddlewareGuard
Biết route là gì?❌ Không✅ Có (biết class, method)
Đọc được decorator?❌ Không✅ Có (Reflector API)
Dùng DI?Hạn chế✅ Đầy đủ
Dùng choCORS, logging raw, body parsingAuth, authorization, feature flags

③ Module System — Hộp kín và cách mở khóa

Module là hộp kín. Mặc định không ai ra vào được. imports và exports là cánh cửa.

Visual: IdentityModule của bạn

IdentityModule
imports: PrismaModule PassportModule
controllers: AuthController
providers: AuthService TokenService JwtStrategy
exports: TokenService

✅ AuthController có thể dùng AuthService — cùng module
✅ AuthService có thể dùng PrismaService — vì imports: [PrismaModule] và PrismaModule exports PrismaService
❌ Module ngoài không thể dùng AuthService — không được export
✅ Module ngoài có thể dùng TokenService — được export

Lỗi phổ biến nhất với Module

// ❌ LỖI: Quên import module
@Module({
  providers: [AuthService],
  // Thiếu imports: [PrismaModule]
})
export class IdentityModule {}

// Error khi chạy:
// Nest can't resolve dependencies
// of the AuthService (?). Please
// make sure PrismaService is
// available in IdentityModule.
// ✅ ĐÚNG
@Module({
  imports: [PrismaModule],
  providers: [AuthService],
})
export class IdentityModule {}

// PrismaModule phải exports
// PrismaService thì mới dùng
// được từ module khác

Global Module — dùng cho PrismaModule

Một số module được dùng ở khắp nơi (Prisma, Config). Thay vì mọi module đều phải imports: [PrismaModule], bạn đánh dấu nó là @Global():

@Global()   ← một lần ở đây, khắp app dùng được
@Module({
  providers: [PrismaService],
  exports:   [PrismaService],
})
export class PrismaModule {}

// Sau đó IdentityModule KHÔNG cần imports: [PrismaModule]
// PrismaService tự động available ở mọi module
⚠️
Đừng lạm dụng @Global() Chỉ dùng cho infrastructure modules (Prisma, Config, Logger). Domain modules không nên global — bạn sẽ mất track ai dùng gì, code khó maintain.

Dynamic Module — PassportModule.register() là gì?

// Trong IdentityModule:
imports: [PassportModule.register({ defaultStrategy: 'jwt' })]

// PassportModule.register() là Dynamic Module
// = một hàm nhận config và TRẢ VỀ một Module object
// Cho phép cùng module nhưng cấu hình khác nhau ở mỗi nơi dùng
// Bạn sẽ thấy pattern này nhiều: JwtModule.register(), TypeOrmModule.forRoot()

④ Kiểm tra — Tự đánh giá mức hiểu

Chọn đáp án đúng. Feedback ngay lập tức.

Q1. Bạn viết một AuthService mới nhưng khi chạy app lỗi "Nest can't resolve dependencies of the AuthService". Nguyên nhân khả năng nhất là gì?

AuthService thiếu decorator @Injectable()
AuthService cần PrismaService nhưng PrismaModule chưa được thêm vào imports của module
AuthService được khai báo trong providers trước PrismaService
PrismaService không có trong exports của PrismaModule

Q2. Request POST /auth/login đến app. @Public() được gắn trên method login(). Guard đọc decorator này ở bước nào trong pipeline?

Middleware đọc trước khi Guard chạy
Guard dùng Reflector để đọc metadata từ handler, quyết định cho qua hay chặn
Pipe kiểm tra decorator trước khi validate body
Handler tự kiểm tra decorator của mình

Q3. IdentityModule có exports: [TokenService]. Điều này có nghĩa là gì?

NestJS tạo thêm một instance TokenService riêng cho module bên ngoài dùng
TokenService chỉ có thể dùng ở module ngoài, không dùng được trong IdentityModule
Module khác có thể imports: [IdentityModule] và sau đó inject TokenService
TokenService trở thành global, mọi module đều dùng được không cần imports

Q4. Bạn muốn thêm một CatalogModule mới cho Phase C. Module này cần dùng TokenService từ IdentityModule để verify token. Bạn cần làm gì?

Copy code của TokenService vào CatalogModule
Inject TokenService trực tiếp vào CatalogService trong constructor
Thêm imports: [IdentityModule] vào CatalogModule, rồi inject TokenService trong CatalogService
Đánh dấu IdentityModule là @Global()
