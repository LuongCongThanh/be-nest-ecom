1. Tại sao cần hai loại token?

JWT access token (AT) là stateless — server ký ra rồi không nhớ gì. Không thể "hủy" một AT đang tồn tại nếu không có blacklist. Đây là đánh đổi thiết kế: stateless = nhanh, nhưng không revoke được ngay.

Loại token TTL Lưu ở đâu Có thể revoke ngay không?
Access Token (AT) 30 phút Memory (client) ❌ Không (stateless JWT)
Refresh Token (RT) 7 ngày DB (refresh_tokens) ✅ Có (set revokedAt)
AT sống ngắn (30 phút) để giảm cửa sổ rủi ro nếu bị lộ. RT sống dài (7 ngày) để UX tốt — người dùng không bị hỏi mật khẩu mỗi nửa tiếng. Khi AT hết hạn, client dùng RT để xin cặp token mới mà không cần nhập lại mật khẩu.

2. Rotation là gì và tại sao làm vậy?

Không rotate: RT cũ dùng được mãi 7 ngày. Nếu attacker lấy được RT, họ có 7 ngày để dùng thoải mái.

Có rotate: Mỗi lần dùng RT để refresh → RT cũ bị đánh dấu usedAt, cặp token mới được cấp. RT cũ không dùng được nữa.

Lợi ích

Cửa sổ exploit thu hẹp xuống còn khoảng thời gian giữa hai lần refresh (thường vài phút đến vài giờ tùy app). Nếu attacker lấy được RT nhưng bạn đã dùng nó trước họ → attacker cầm token vô dụng.

Flow Rotation — 7 bước

1
Client gửi POST /auth/refresh với raw refresh token trong body
2
Server hash token nhận vào → tìm trong DB theo tokenHash
3
Nếu usedAt != null → replay detected → kill toàn family → 401
4
Nếu revokedAt != null → token đã bị revoke → 401
5
Nếu expiresAt < now → token hết hạn → 401
6
Set usedAt = now trên token cũ (mark consumed)
7
Tạo RT mới với cùng familyId, ký AT mới, trả cặp token mới về client

3. Replay Detection — "Kill Family" hoạt động thế nào?

Đây là phần bảo mật tinh tế nhất. Hãy hình dung tình huống này:

Tình huống tấn công

1. User Alice có RT_1
2. Attacker Eve đánh cắp RT_1 (man-in-the-middle, XSS, rò rỉ...)
3. Alice dùng RT_1 → server cấp RT_2, đánh dấu RT_1.usedAt = now
4. Eve bây giờ dùng RT_1 (đã stolen) → server phát hiện usedAt != null

Lúc này server biết một điều quan trọng: cả Alice lẫn Eve đang cầm token trong cùng chain — Alice cầm RT_2, Eve cầm RT_1 (cũ). Không biết ai là hợp lệ vì server không theo dõi device/IP.

Phản ứng đúng: revoke toàn bộ family → buộc cả hai phải đăng nhập lại bằng mật khẩu. Alice bị phiền một chút (phải login lại), nhưng Eve không thể tiếp tục dùng tài khoản Alice.

familyId nhóm tất cả RT sinh ra từ cùng một login session thành một "family". Kill family = đăng xuất phiên đó khỏi mọi thiết bị đang rotate trong chain đó. Đây là lý do tại sao RT mới luôn kế thừa familyId của RT cũ — không tạo randomUUID() mới. 
// Khi phát hiện replay: revoke toàn bộ family trong 1 query
await tx.refreshToken.updateMany({
  where: { familyId: tokenRecord.familyId },  // toàn bộ chain
  data: { revokedAt: new Date() },
});
throw new UnauthorizedException({
  code: 'REFRESH_TOKEN_REPLAY_DETECTED',
  message: 'Token reuse detected. All sessions revoked.',
});

4. Hash-based Storage — Tại sao không lưu raw token?

DB chỉ lưu tokenHash = SHA-256(rawToken), không bao giờ lưu raw token.

Lưu raw tokenLưu hash (SHA-256)
DB bị dump ❌ Attacker lấy hết token, impersonate mọi user ✅ Chỉ có hash vô nghĩa, không forge được
Lookup Tìm trực tiếp Hash token nhận vào rồi tìm theo hash
Tại sao SHA-256 được (không cần bcrypt)? Raw token là randomUUID() — có 122 bit entropy. SHA-256 chỉ cần chống DB dump, không cần chống brute force vì token quá ngẫu nhiên. 
// SHA-256 one-way hash — fast, không cần salt
private hashRefreshToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}

// Khi refresh: hash token nhận vào rồi tìm trong DB
const tokenHash = this.hashRefreshToken(refreshTokenValue);
const tokenRecord = await tx.refreshToken.findUnique({
  where: { tokenHash },  // tìm theo hash, không theo raw value
});

5. Prisma Transaction — Tại sao cần atomic?

Hàm refresh() thực hiện hai thao tác DB phải xảy ra cùng nhau hoặc không xảy ra gì:

  1. Mark token cũ: usedAt = now
  2. Tạo token mới: insert record mới vào refresh_tokens
Không có transaction

Nếu server crash sau bước 1 (mark used) nhưng chưa tạo token mới → user mất phiên làm việc, phải login lại. Tệ hơn: nếu bước 1 fail nhưng bước 2 thành công → token mới tồn tại nhưng token cũ chưa bị mark → replay protection bị bypass.

Có transaction

Cả hai bước là all-or-nothing. Nếu bất kỳ bước nào fail → DB rollback về trạng thái ban đầu. Không có trạng thái nửa vời.

return this.prisma.$transaction(async (tx) => {
  // tx là transaction client — dùng thay prisma trong block này

  // Bước 5: mark used
  await tx.refreshToken.update({
    where: { id: tokenRecord.id },
    data: { usedAt: new Date() },
  });

  // Bước 6: tạo token mới — cùng familyId
  await tx.refreshToken.create({
    data: { userId, familyId: tokenRecord.familyId, tokenHash: newHash, expiresAt },
  });

  return { accessToken, refreshToken: newRefreshTokenValue };
}); // nếu exception ném ra trong block → tự động rollback

6. Trade-off quan trọng: AT vẫn sống sau khi RT bị revoke

Trade-off

Khi RT bị revoke (logout, logout-all, replay detected...), AT tương ứng vẫn còn hiệu lực cho đến khi hết TTL (tối đa 30 phút). Một API protected chỉ verify AT — không check RT.

Đây là đặc tính thiết kế có chủ ý, không phải bug. AT là JWT stateless — server ký ra rồi không lưu trạng thái. Để revoke AT ngay lập tức cần một blacklist (thường dùng Redis) — mỗi request phải check Redis xem AT có bị blacklist không.

Không blacklist (Task 13)Có blacklist Redis (Phase D)
Revoke AT ngay ❌ Không ✅ Có
Latency mỗi request ✅ Không thêm ⚠️ +1 Redis lookup
Complexity ✅ Đơn giản ⚠️ Cần Redis, thêm expiry logic
Rủi ro AT còn sống tối đa 30 phút sau revoke Gần như zero nếu implement đúng

Hầu hết app thực tế dùng AT TTL 5–15 phút để giảm rủi ro này xuống mức chấp nhận được mà không cần Redis.
