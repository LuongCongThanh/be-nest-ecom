NestJS Module System:
Tại sao lại có Module?

Hiểu tại sao NestJS dùng Module — không chỉ cách dùng

Vấn đề Module giải quyết

Hãy tưởng tượng bạn có 3 file TypeScript thuần:

// Không có framework nào cả
const prisma = new PrismaClient();
const categoryRepo = new CategoryRepository(prisma);
const categoryService = new CategoryService(categoryRepo);
const categoryController = new CategoryController(categoryService);

Code này hoạt động được. Nhưng có 3 vấn đề:

  1. Ai tạo ra ai? — Bạn phải nhớ thứ tự và dependencies của tất cả object.
  2. Shared instances — Nếu 2 service cùng cần PrismaClient, bạn phải tự đảm bảo chỉ tạo 1 instance duy nhất.
  3. Testing — Để test CategoryService, bạn phải tạo cả PrismaClient thật.

NestJS giải quyết cả 3 vấn đề này với Dependency Injection (DI) Container.

DI Container là gì — thực sự

DI Container là một "registry" — một bản đồ từ token (thường là class) đến instance của nó. Khi bạn viết:

@Injectable()
export class CategoryService {
  constructor(private repo: CategoryRepository) {}
}

Bạn đang nói với NestJS: "Khi cần tạo CategoryService, hãy tự tìm CategoryRepository trong registry và inject vào."

Nguyên tắc cốt lõi

Bạn không gọi new. NestJS làm điều đó cho bạn — và đảm bảo mỗi class chỉ được tạo một lần (singleton theo mặc định) trong scope của Module.

Module = Ranh giới rõ ràng

Nếu DI Container là cái registry, thì Module là cái phạm vi (scope) của registry đó.

┌─────────────────────────────────────────────────┐
│                  AppModule                      │
│                                                 │
│   ┌──────────────────┐   ┌──────────────────┐  │
│   │   CatalogModule  │   │    OrderModule   │  │
│   │                  │   │                  │  │
│   │  CategoryService │   │  OrderService    │  │
│   │  ProductService  │   │  OrderRepository │  │
│   │  CategoryRepo    │   │                  │  │
│   └──────────────────┘   └──────────────────┘  │
│                                                 │
│   ┌──────────────────┐                          │
│   │   SharedModule   │  ← exports PrismaService │
│   │   PrismaService  │    sang mọi module khác  │
│   └──────────────────┘                          │
└─────────────────────────────────────────────────┘

CategoryService không thể tự inject OrderService trừ khi OrderModule export nó và CatalogModule import OrderModule. Đây là ranh giới có chủ đích — ngăn code của bạn trở thành mạng nhện dependencies.

Anatomy của một Module trong dự án bạn

Trong be-nest-ecom, CatalogModule sẽ trông như thế này:

@Module({
  imports: [PrismaModule],      // Lấy PrismaService từ module khác
  controllers: [
    CategoryController,    // Xử lý HTTP request
    ProductController,
  ],
  providers: [
    CategoryService,       // Business logic — private mặc định
    ProductService,
    CategoryRepository,    // Data access layer
    ProductRepository,
  ],
  exports: [
    CategoryService,       // Chỉ export những gì module khác cần
  ],
})
export class CatalogModule {}
Quy tắc thực tế

providers = những gì module này tự tạo ra và quản lý.
exports = tập con của providers mà module khác được phép dùng.
imports = những module khác mà mình cần dùng exports của họ.

Tại sao singleton là mặc định?

Mỗi provider trong một Module được tạo một lần duy nhất khi app khởi động, và instance đó được share cho mọi class cần nó trong cùng scope.

Điều này có nghĩa là:

  • CategoryService và ProductService cùng inject CategoryRepository → chúng nhận cùng 1 instance
  • Không lãng phí memory, không race condition trong initialization
  • Dễ test: inject mock thay thế toàn bộ dependency
Cạm bẫy phổ biến

Nếu một provider có state mutable (biến đổi theo request), singleton scope sẽ gây lỗi race condition. Trong trường hợp đó dùng REQUEST scope — nhưng đây là ngoại lệ, không phải quy tắc.

PrismaModule — Pattern trong dự án thực

Dự án be-nest-ecom của bạn có (hoặc sẽ có) một PrismaModule được share toàn bộ app:

@Module({
  providers: [PrismaService],
  exports: [PrismaService],   // Cho phép mọi module import
})
export class PrismaModule {}

// PrismaService extends PrismaClient — singleton duy nhất
@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit {
  async onModuleInit() {
    await this.$connect();
  }
}

Khi CatalogModule imports PrismaModule, nó nhận được cùng 1 connection pool — không tạo kết nối database mới.

Kiểm tra hiểu bài

Câu hỏi 1 / 3
Bạn muốn OrderService trong OrderModule có thể dùng CategoryService từ CatalogModule. Bạn cần làm gì?
  • Thêm CategoryService vào providers của OrderModule
  • Export CategoryService từ CatalogModule, sau đó import CatalogModule vào OrderModule
  • Đánh dấu CatalogModule là @Global()
  • Inject CategoryService trực tiếp mà không cần import
Câu hỏi 2 / 3
Trong NestJS, mặc định một @Injectable() provider có lifecycle thế nào?
  • Tạo instance mới mỗi lần được inject (transient)
  • Tạo instance mới cho mỗi HTTP request (request scope)
  • Một instance duy nhất dùng chung trong module (singleton)
  • Singleton trong production, transient trong development
Câu hỏi 3 / 3
Sự khác biệt giữa providers và exports trong @Module() là gì?
  • providers và exports là như nhau, có thể dùng cái nào cũng được
  • exports tạo thêm instances, providers chỉ khai báo type
  • exports là alias của providers cho modules con
  • providers = những gì module tạo và quản lý; exports = những providers nào được phép dùng bởi module bên ngoài
